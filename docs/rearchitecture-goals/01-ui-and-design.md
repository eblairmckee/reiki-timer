# UI and design: establish the system's contract model

Determine the right ownership, abstraction boundaries and composition model for the app's shared visual and interaction language. Implement warranted changes and establish how its quality obligations will be maintained as consumers evolve.

Apply the [shared purpose and session protocol](00-prerequisites.md), including the maintainer persona and decision matrix. Discover current implementation facts from their source.

The Phase 00 handoff started this phase as an audit only. The user subsequently authorized the recommendations with “go ahead and make the recommended changes.” The audit below is historical evidence; the implementation handoff records the resulting changes and verification.

```text

Follow the shared purpose, session protocol and current authorization scope. Resolve the system's architectural decisions into concrete recommendations and a validation approach for its contracts and quality ownership.
```

## Decisions to resolve

- **Ownership and variation.** Which visual and interaction decisions should change together, and which differences need independent ownership? Assess whether present abstractions express those relationships without duplication, accidental coupling or excessive generality.
- **Composition and extension.** How should consumers combine and extend shared capabilities? Decide the supported boundaries and responsibilities, including what consumers must understand and what the system should handle. Assess the effects of changing a shared decision across existing and plausible independent consumers.
- **Contract maintenance.** What guarantees must survive future changes, and which require accountable judgment? Use the matrix to assign effective controls and discovery mechanisms to those guarantees. Review existing tests and guidance against the resulting contracts.

## Outcome and evidence

Implement the selected architecture and keep enduring contracts at their owning source. Explain consequential choices through their consumer needs, alternatives, compatibility and maintenance implications. Existing designs can be retained with a reason.

Validate the properties each decision claims: appropriate change propagation, supported composition, intended design/interaction quality and sustainable maintenance. Fresh-agent tasks assess discovery and use of those contracts. Architectural conclusions also require evidence about ownership and dependencies. Passing tasks alone do not settle abstraction quality.

Completion requires a justified system contract model, implemented changes, evidence for the chosen quality owners and explicit remaining human judgments. Avoid reproducing the system's API or styling documentation in this plan.

## Handoff and cleanup

Pass shared tooling needs to Phase 02 and consumer obligations to Phase 03. Carry unresolved decisions with an owner and their effect on acceptance. Finish with the [cleanup handoff](00-prerequisites.md#handoff-and-cleanup). Do not stage or commit unless explicitly asked.

### Material findings and proposed quality owners

**1. Give summary details an explicit activation contract — priority: high.** Accepted conventions: brand/accessibility, composition and self-documenting contracts. [summary.tsx:7–20,49–73](../../src/components/design-system/button-group/summary.tsx#L7) calls details noninteractive and uses a focusable fieldset. At the audited revision `b2f3921`, `use-hover-details.ts:49–71` suppresses pointer-origin focus, opens only for mouse/hovering pen movement, and has no click/touch-open handler. The real details contain the keyboard-scrollable [timeline list](../../src/components/molecules/timeline/index.tsx). This is a source-demonstrated missing activation path and an underspecified focusable-content contract; device/assistive-technology behavior has not been observed here.

Recommend a named button controlling a sibling details region, with touch/Enter/Space activation, an exposed expanded state, Escape dismissal and focus return. Hover may remain an enhancement. Specify that informational content may include a focusable scroll region; keep arbitrary action menus outside this contract. Reuse existing disclosure foundations where their state/semantics fit, preserving overlay alignment. Alternatives: keep hover-only content with a separate timeline action (duplicates access paths), or make details permanently visible (changes density). **Owners:** API/default behavior and colocated JSDoc; component tests for state, Chromium for touch activation, focus transfer, scrolling and exit inertness; human review for affordance/placement. Types cannot prove arbitrary ReactNode contents are noninteractive. Added activation state and a few browser cases cost more than a wording fix but address an actual inaccessible path; mobile layout and screen-reader announcement remain unknown. Preserve the trailing action and repeated chime activation during validation.

**2. Make Button's variation promises truthful — priority: medium.** Accepted conventions: meaningful public contracts and intentional variation; fully independent variant axes are only a recorded choice. [ButtonProps](../../src/components/design-system/button/index.tsx#L14) describes intent as independent of appearance and size as control dimensions. [Intent CSS](../../src/components/design-system/button/style.css#L133) defines intent colors, but [frost/inset CSS](../../src/components/design-system/button/style.css#L241) uses fixed material ink/fill instead. Frost icon dimensions also use one custom-property size regardless of `sm/md/lg`; word buttons only distinguish `lg`. The [error-link test](../../test/browser/design-entrypoints.test.tsx#L225) proves that combination, not all advertised combinations.

Recommend appearance-specific types/docs that reject unsupported semantic emphasis and explain frost sizing, preserving current valid caller behavior. If design needs error-colored frost, implement and approve that treatment explicitly instead of silently accepting an ineffective prop. The alternative is implementing every Cartesian combination, with substantially more brand decisions and state coverage. **Owners:** API/types for supported combinations, JSDoc for dimensions and defaults, rendered tests for promised variation, human review for new treatments. Existing timer callers mostly use defaults, so observed migration scope is small; future/upstream compatibility is unknown and must be checked before narrowing. Compile checks cannot prove that a permitted intent is perceptible.

**3. Clarify composition responsibilities at declarations — priority: medium.** Accepted conventions: self-documenting APIs, accessible naming and reusable callback language. [Collapsible docs](../../src/components/design-system/collapsible/index.tsx#L8) describe trigger/panel composition and automatic relationships; [TimerSettings](../../src/features/timer/components/timer-settings/timer-settings.tsx) instead uses controlled roots with Switch and manually supplies panel IDs/`aria-controls`. [LinkButton's anchor branch](../../src/components/design-system/link-button/index.tsx#L14) claims navigation but inherits optional `href`. Button's callback prose mentions repeated “previews,” although preview commands belong to ChimePicker.

Recommend one concise external-controller Collapsible example documenting who owns state, relationships and focus when a panel closes; retain the native trigger example and do not change Switch into a disclosure button. Require `href` for LinkButton's navigation branch, retaining `as="button"` for commands. Describe Button repeat activation without feature vocabulary. Prefer these source corrections over a new composition skill or JSDoc word-count rule. **Owners:** types for the link branch; documentation for callback meaning and external-controller composition; existing behavior tests plus a focused real-browser closed-panel Tab check. This adds little recurring context but has no measured discovery benefit yet. Dial already requires a name and separates visible/accessibility value formatting; its narrow [input API](../../src/components/design-system/dial/index.tsx#L11) lacks description forwarding. Add a targeted `aria-describedby` capability when a described Dial consumer needs it, rather than expose unrestricted native handlers that could override its gesture contract.

**4. Declare the supported styling surface without publishing the DOM — priority: medium.** Accepted conventions: reuse, meaningful names and discoverable ownership; exact selector/override policy is provisional. Button documents one root inset override, while [settings CSS](../../src/features/timer/components/timer-settings/style.css) consumes Dial/Switch sizing variables and selects `.dial` to decide feature spacing. [Finish dialog CSS](../../src/features/timer/components/finish-timer-dialog/style.css) selects the system's button marker for product spacing. These dependencies work today but their compatibility status is not stated at the affected declarations.

Recommend documenting the already-needed root sizing hooks beside Button/Dial/Switch, and the ink/lettering/backdrop utilities at their CSS owners. Give feature-owned spacing an explicit feature class or local layout flag instead of discovering a child implementation class. Treat internal frost faces/ripples as system-owned; peer component selectors can remain an internal system dependency with co-change tests. Alternatives: expose every selector as public (large compatibility burden), ban all selectors (ignores valid system composition), or add a universal slot API (unneeded complexity). **Owners:** public JSDoc/CSS documentation and human review; types only where a real prop expresses the variation; rendered propagation tests for documented hooks. Keep current reusable names and owner-prefixed parts; no evidence justifies a token-wide rename or mechanically enforcing semantic naming. Discovery and review-time savings are hypotheses, not measured results.

**5. Preserve theme color ownership; stop equating it with a hex ban — priority: medium, tooling handoff.** Accepted conventions: theme-owned application colors, legitimate transparency/currentColor/forced-color exceptions, preference for installed tooling. [biome.json](../../biome.json) enables `noHexColors` outside the theme. A temporary file trial through `bun run lint <path>` accepted raw `rgb(1 2 3)` and a semantic variable (exit 0), and rejected `#123456` with `lint/style/noHexColors` (exit 1). Therefore that rule does not enforce the accepted ownership boundary; its diagnostic even suggests color functions. This is an enforcement gap, not evidence of widespread raw colors in the implementation.

Keep theme colors and the [Olyx alias bridge](../../src/components/design-system/styles/olyx-compat.css) as their current owners. Document the narrow rendering exception: [Atmosphere](../../src/components/design-system/atmosphere/index.tsx#L69) serializes resolved theme pigments into shader/fallback values; it is not an independent palette. **Owners:** documentation/human review immediately; Phase 02 evaluates lint only against actual CSS, JSX/SVG and renderer inputs, with semantic references and platform colors as valid cases. A blanket color-function ban would reject legitimate derived colors; a standalone graph checker adds parsing and exception upkeep without measured benefit. Do not restore it. Keep unused-token reporting advisory and include alias/runtime consumers before treating a token as unused. Rule coverage, false positives and ongoing CI cost beyond this CSS trial remain unknown; no new enforcement was installed.

**6. Separate shared motion decisions from different mechanisms — priority: medium.** Accepted conventions: reuse of decisions that should change together and reduced-motion responsibility. [motion.ts](../../src/components/design-system/shared/motion.ts) and [theme.css](../../src/components/design-system/styles/theme.css#L169) share scene clocks already compared by [theme.test.ts](../../test/browser/theme.test.ts#L9); CSS transitions and JS control/disclosure springs intentionally have different mechanisms. Component-local dialog/group durations and the summary's local opacity fade do not, by themselves, prove duplication. However, [Button CSS](../../src/components/design-system/button/style.css#L193) still scales non-frost actions on press, while its [reduced-motion rule](../../src/components/design-system/button/style.css#L443) only covers frost icon reshape/hint behavior.

Recommend explicitly suppressing nonessential transform/reshape motion for every supported Button appearance under reduced motion, while retaining immediate state feedback. Keep meaningful component-specific timings unless visual review establishes that they must co-change; do not generate a universal CSS/JS token pipeline merely to remove similar numbers. **Owners:** shared defaults/CSS, behavioral tests and human motion review. [Vitest](../../vitest.config.ts#L57) defaults Chromium to reduced motion, and [unit setup](../../test/setup.ts#L5) disables native `Element.animate`; the Atmosphere reset fixture exercises a narrower mocked preference path. Add a small normal-motion browser set covering interrupted reveal, rapid toggle, pointer cancellation and a preference change mid-animation, alongside reduced-motion cases. This costs browser runtime but proves behavior that static duration equality cannot. Exact timing/aesthetic acceptance and added CI duration remain unmeasured.

**7. Treat rendered contrast as unresolved, with a bounded validation plan — priority: high before visual acceptance.** Accepted convention: brand/accessibility; historical numeric thresholds are evidence, not automatically universal policy. [axe coverage](../../test/browser/accessibility.test.tsx#L44) logs incomplete checks while asserting zero reported violations. [Theme tests](../../test/browser/theme.test.ts#L94) bound some composited surfaces and sample atmosphere mixtures; they do not read rendered shader pixels. More specifically, [the control model](../../src/components/design-system/atmosphere/ink-strength.ts#L54) assumes 24% white backing, and [the test](../../test/browser/theme.test.ts#L168) uses the well-light token, while selected frost uses a different fill plus layered sheen/shade. That is an unproven mapping, not a measured contrast failure. The glass-dialog rendering, focus rings and translucent combinations also need actual surface-specific evidence.

Recommend retaining the useful numerical tests, tracing their assumptions to each actual rest/hover/selected surface, then inspecting setup, expanded timeline, selected chime, finish dialog and saved state over relevant palette extrema. Include narrow layout/zoom, keyboard focus, forced colors and reduced transparency. **Owners:** tests for calculable relationships and named states; human visual/accessibility review for appearance and unresolved axe nodes. Classify text/control/focus acceptance before choosing thresholds; do not use opacity caps or screenshot appearance alone as accessibility proof. Exhaustive screenshot permutations would be expensive and GPU-sensitive; targeted captures plus documented contrast measurements are the preferred first step. The existing dev server was confirmed at `localhost:5173`, but the in-app browser returned “Local browser use is disabled in Work settings.” No rendered verdict is claimed; manual inspection remains pending access.

**8. Keep tests tied to guarantees, not accidental geometry — priority: medium.** Accepted conventions: sustainable quality ownership and maintenance; exact dimensions/private-selector assertions remain provisional. [Entry-point tests](../../test/browser/design-entrypoints.test.tsx#L62) hardcode input/group sizes, and [frost tests](../../test/browser/design-entrypoints.test.tsx#L208) hardcode 48px, 12px blur and a 0.065 inset ratio. These can detect missing CSS, but also reject legitimate token changes. Conversely, [scoped material propagation](../../test/browser/design-entrypoints.test.tsx#L307), stable primary actions, native activation and focus tests express useful shared guarantees. Happy DOM's [Collapsible test](../../src/components/design-system/collapsible/collapsible.test.tsx#L55) explicitly cannot establish inert Tab exclusion.

Recommend retaining installed-entrypoint smoke coverage, repeat activation, native semantics and scoped propagation. Replace redundant fixed-value assertions with declared-token/relationship checks unless the design owner accepts a fixed dimension; use browser tests for real focus containment/exclusion and layout relationships. Keep a few private selectors inside system-owned material tests when necessary to observe the promised face/well behavior; a blanket selector ban would reduce coverage. Pure numerical contrast work can move to unit tests only if browser color-resolution coverage remains. **Owners:** component tests for behavior, Chromium for browser-dependent properties, human review for acceptance criteria. This trades one-time assertion review for less routine restyle churn; actual suite savings are unknown. Do not delete cases merely because they use pixels or internal markup.
