# Repository conventions: recovered intent for the audits

This is the starting reference for audits of UI/design, tooling and the product repo. It records the intended conventions recovered from user decisions and maintained guidance. Implementation and enforcement still need assessment through the [maintainer persona](../.agents/skills/design-system-maintainer/SKILL.md) and [decision matrix](../.agents/skills/design-system-maintainer/references/quality-ownership.md).

**Accepted intent** below has direct user direction or an approved plan behind it. **Recorded choices** have source or historical-rule evidence, but their exact formulation needs validation. An existing checker, passing fixture or merged implementation alone does not establish acceptance. Later instructions supersede earlier proposals, particularly for enforcement and hosted reviews.

## Product organization and shared component taxonomy

Adopted November 7, 2026 during Phase 03. Directories communicate concern and state ownership. The [Phase 03 migration record](rearchitecture-goals/03-product-repo.md) records why existing files moved; routine work starts from this convention and affected source contracts.

The user's current directions establish these placement rules:

- Feature-specific UI belongs in `src/features/<feature>/components/`, with feature screens, hooks, data, domain rules and side effects organized by concern. Do not nest atomic tiers such as `organisms/` inside a feature.
- Shared application components use `src/components/atoms/`, `molecules/` and `organisms/`. The established `src/components/design-system/` remains the adapted foundation; use its public controls instead of duplicating them in the atomic tiers.
- A **molecule** combines smaller parts for one reusable purpose and owns no interaction or product state. Values, content and actions come from the caller.
- An **organism** composes reusable parts and owns coordinated state/lifecycle. Its contract may expose controlled or uncontrolled operation; those modes and change notifications must be explicit. Feature-specific workflows remain feature components even when they own state.
- Shared utilities and hooks have concern-based homes under `src/utils/` and `src/hooks/`. App startup/routing policy has an app owner. Root-level entrypoints and generated framework files are explicit exceptions, not a home for miscellaneous helpers.

The recovered historical definition of an **atom** is a focused reusable primitive, such as a button, input or label. Historical molecules combined smaller parts for one interaction/purpose, and organisms coordinated substantial sections. The current user direction adds the explicit state-ownership distinction above. The recovered text does **not** establish that the exact stateless/controlled/uncontrolled wording was present before; do not invent that provenance.

State classification concerns what the component owns. Reading an inherited preference or presence context, holding a DOM ref, and using a stateful foundation do not themselves mean the composition owns the caller's selection or workflow. These should be explained at the contract rather than classified by a mechanical `useState`/Hook-name scan. A controlled settings form containing timer rules remains feature-specific; statelessness alone does not make its product copy reusable.

Promotion should be evaluated through a neutral typed API, a current consumer and a concrete independent usage example. Two already-shipping features are not a prerequisite. Move reusable behavior and styling together; keep domain interpretation, routes, asset selection and product copy at the feature boundary. Call promoted components directly when an old wrapper only forwards props or re-exports them. A feature adapter that actually constructs domain-specific content remains useful.

Keep a component's CSS, private helpers and focused tests with its owner. Shared utilities must not import features or component implementations; shared UI must receive feature data/actions rather than import them. Create directories when populated. Use named component implementation files inside feature component folders. A shared component may use `index.tsx` as its actual implementation; avoid forwarding barrels and compatibility re-exports for internal moves.

The adopted source structure has these owners:

| Directory | Responsibility |
| --- | --- |
| `src/app/routing/`, `app/styles/` | Router instance, route-transition policy and global application styles. |
| `src/routes/` | Thin TanStack file-route adapters; the generator owns `src/routeTree.gen.ts`. |
| `src/components/design-system/` | Adapted foundations, brand tokens/materials/motion and system-specific helpers. |
| `src/components/{atoms,molecules,organisms}/` | Reusable app presentation/composition, classified by the state contract above. |
| `src/hooks/`, `src/utils/<concern>/` | Neutral React/platform lifetimes and non-React utilities; no feature dependencies. |
| `src/features/<feature>/screens/` | Route/view composition, navigation transactions and focus choreography. |
| Feature `components/` | Product-specific UI, including controlled forms and meaningful domain-content adapters. |
| Feature `hooks/`, `state/` | React lifecycle/commands and context contracts, respectively; one authoritative state owner. |
| Feature `model/`, `data/` | Pure domain types/validation/calculations and product catalogues/palettes. Models do not import browser services or components. |
| Feature `services/` | Browser/external I/O and compatibility/failure handling. |
| Feature `utils/`, `styles/` | Domain-to-presentation adapters and genuinely shared feature styles. Private component helpers/styles stay with the component. |

`src/main.tsx` remains the deliberate bootstrap entrypoint. Keep focused tests next to their owner; whole-feature navigation/integration tests live with the feature layout, and actual-browser evidence lives under `test/browser/`. Name a file for its responsibility (`timer-config`, `sound-player`), not an accumulating `helpers` or `lib` bucket. Add only the directories a feature needs.

Dependencies flow from routes/app into features and shared UI, from feature screens into their components/hooks/model/services, and from shared compositions into neutral foundations. Shared components, hooks and utilities never import features. Feature models may use feature data and neutral utilities, but never browser services. Avoid cycles and imports of private system material internals. Keep `components.json` pointed at the established design-system owner.

Examples: TimerSettings remains a feature component because its labels and cue rules are product-specific; its controlled Choicebox receives option content and activation callbacks directly. TimerSummary remains a useful feature adapter because it constructs domain-specific items for SummaryList. Timeline receives caller-formatted content; `timeline-items.tsx` interprets timer cues. CyclingAtmosphere owns neutral cycling state and exposes explicit controlled/uncontrolled modes; chakra palettes remain feature data. SoundPlayer receives URLs; the feature hook selects chime assets and error copy. Scene/glyph atoms keep motion/Icon foundations. Do not migrate established design-system controls into duplicate atomic primitives.
