# Composition and ownership

Read the affected public APIs and consumers. Sketch normal usage and meaningful variation before growing a contract. Use the app-owned system's public foundations before introducing another primitive. For shared UI, read [atomic contracts](rules/atomic-ui.md#common-contract), then the selected tier. Use [UI promotion](../ui-promotion/SKILL.md) when scope or ownership changes; it owns placement decisions.

- Choose composition for what the consumer needs to author. Ordinary props suit small fixed relationships; children suit caller-authored structure; named slots clarify distinct content responsibilities; a render callback supplies owned state/data to caller-authored content. Use compound parts and context when independently placed parts need the same scoped contract. A provider is not a default solution to all prop passing.
- Put coordinated state at the nearest common owner of **all** participants, including siblings outside a visual frame. Let each participant read that owner and request actions. Do not relay rendering state upward through Effects or imperative refs. Keep independent instances isolated. Context may expose state and actions while its owner uses local state or an existing store; missing required scope should fail clearly.
- Separate controlled value, uncontrolled initial default and change notification. Determine control by the documented presence contract, preserving `false`, `0` and empty strings. Controlled parts reflect the parent even when a requested change is declined. Do not silently synchronize a second local copy. Keep a component's identity stable through ordinary parent renders; stable item keys preserve each item's state across reordering.
- Preserve the native element's props and ref type, accessible names, labels/descriptions, errors, event timing and cancellation through wrappers. Use the installed React/library's ref and event-composition contracts. A wrapper must not accidentally submit, activate twice or bypass a consumer's prevented action. Expose only supported props and children; forward promised content or omit that capability from the public type. Name promoted APIs for reusable purpose, scope and state. Document prop/slot purpose, expected content, accessible-naming responsibility and callback timing at the declaration; useful meaning cannot be established by word counts.
- Use a discriminant or composition for mutually exclusive modes, while independent state such as disabled remains a boolean. If modes need unrelated providers, data or workflows, compose them at the feature instead of adding business-specific switches to shared UI.

Check caller-owned copy/actions, controlled updates, independent instances, native/ref behavior and applicable layout/theme states. Type and lint checks reject some invalid contracts and import directions; they cannot establish a coherent responsibility. Explain remaining architectural tradeoffs without prescribing one valid implementation shape.
