# Composition and ownership

Read the affected public APIs and consumers. Sketch normal usage and its meaningful variation before growing a contract. Preserve the app's existing directories: adapted primitives in `src/components/design-system`, shared app UI in atoms/molecules/organisms, and product-specific UI inside its feature. Atomic categories describe responsibility, not element count or a required hierarchy inside features.

- An atom is a focused primitive. A molecule serves one reusable purpose and owns no interaction or product state; values and actions come from its caller. An organism owns coordinated state/lifecycle across reusable parts. Reading preference context, holding a DOM ref or using a stateful foundation does not itself make a molecule the workflow owner. These are the repository’s current classification rules; follow the directory boundaries in [AGENTS](../../../AGENTS.md#repository-boundaries). Keep API clients, routes, analytics, permissions, product copy and business decisions at the feature boundary. Promote a component when independent consumers need the same public behavior, not merely because two wrappers look alike.
- Choose composition for what the consumer needs to author. Ordinary props suit small fixed relationships; children suit caller-authored structure; named slots clarify distinct content responsibilities; a render callback supplies owned state/data to caller-authored content. Use compound parts and context when independently placed parts need the same scoped contract. A provider is not a default solution to all prop passing.
- Put coordinated state at the nearest common owner of **all** participants, including siblings outside a visual frame. Let each participant read that owner and request actions. Do not relay rendering state upward through Effects or imperative refs. Keep independent instances isolated. Context may expose state and actions while its owner uses local state or an existing store; missing required scope should fail clearly.
- Separate controlled value, uncontrolled initial default and change notification. Determine control by the documented presence contract, preserving `false`, `0` and empty strings. Controlled parts reflect the parent even when a requested change is declined. Do not silently synchronize a second local copy. Keep a component's identity stable through ordinary parent renders.
- Preserve the native element's props and ref type, accessible names, labels/descriptions, errors, event timing and cancellation through wrappers. Use the installed React/library's ref and event-composition contracts. A wrapper must not accidentally submit, activate twice or bypass a consumer's prevented action. Expose only supported props and children; forward promised content or omit that capability from the public type. Document prop/slot purpose, expected content, accessible-naming responsibility and callback timing at the declaration; useful meaning cannot be established by word counts.
- Use a discriminant or composition for mutually exclusive modes, while independent state such as disabled remains a boolean. If modes need unrelated providers, data or workflows, compose them at the feature instead of adding business-specific switches to shared UI.

Justify promotion with a neutral typed API, a current consumer and a concrete independent usage example; two already-shipping features are not a prerequisite. Check caller-owned copy/actions, controlled updates, independent instances, native/ref behavior and the applicable layout/theme states. Type and lint checks reject some invalid contracts and import directions; they cannot establish that a molecule has a coherent responsibility. Explain the boundary and any remaining architectural tradeoff without prescribing one valid implementation shape.
